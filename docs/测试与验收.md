# 测试与验收

引擎、内联引擎、发行包是三个不同的东西，任何一处不一致都会让"测试全绿但玩家拿到旧代码"。
因此验收分四层，**顺序不要跳**。

## 第 1 层：引擎单元测试（最快，改逻辑先跑它）

```bash
node work/tools/engine_test.js          # 全部
node work/tools/engine_test.js 旅行      # 只跑名字匹配的用例
```

- 期望：**373 passed, 0 failed**
- 未包含客户端美术资源时（最小仓库），依赖图片尺寸的那条用例会输出
  `SKIP ...（缺少客户端美术资源）` 而不是失败，结果形如
  `372 passed, 0 failed, 1 skipped`
- 每个用例在独立临时目录里创建全新引擎，互不污染；可直接读写 `engine.state` 构造场景
- 涉及随机的用例一律用**统计断言**（例如"40 趟里多数落在该区域"），避免偶发失败
- 覆盖范围：存档安全、背包与桌子、旅行与目的地、相册、图鉴、商店与礼包拆包、
  访客与邮件、任务与称号、日历、料理、抽奖、手工品、活动窗口、引导步进等

## 第 2 层：打包物验收（内联引擎与浏览器桩）

```bash
node work/tools/verify_bundle_save.js       # 存档槽位、回退链、写入失败上报
node work/tools/verify_bundle_baglock.js    # item_set_bag_completed 真的把青蛙送出门
node work/tools/verify_bundle_a_tier.js     # 合并进来的官方内容在包里能正常交易
node work/tools/verify_editor_new_content.js # 存档编辑器悬浮球包含新增内容
```

这一层加载的是**构建产物**（`work/run/web/__offline-engine.js`）本身，
用来抓"引擎改了但没重建内联文件"这类问题。

## 第 3 层：发行物验收（打进包里的那份资源）

```bash
python work/tools/verify_shipped_*.py        # 20 个文件，逐个 PASS
```

它们检查的是**发行包内**的资源与引擎（相册、动画、胶囊、料理、家具、礼品盒、
图层、抽奖、动态、故事、引导、访客、天气、许愿池…），而不是工作区里的源文件。

打包身份另有两个必须通过的检查：

```bash
python work/tools/apk_identity.py            # 期望 RESULT: OK
python work/tools/test_port_policy.py        # 期望 11 PASS
pwsh   work/tools/test_launcher_port.ps1     # 期望 28 PASS
```

`apk_identity.py` 逐文件比对 APK 内的 `assets/game/**` 与工作区，并校验它是
**干净外壳**而不是原包的重打包 —— 后者能装上但会卡在渠道登录界面。

## 第 4 层：真页面探针（headless Edge）

```bash
cd work/run/web && python -m http.server 8231        # 另开终端
node work/tools/cdp_drive.js --url http://127.0.0.1:8231/index.html --fresh `
  --wait 9000 --settle 3000 `
  --step in:work/tools/probe_travel_map.js `
  --step log --step shot:shot.png
```

`cdp_drive.js` 的分步指令：

| 指令 | 作用 |
|---|---|
| `eval:<js>` / `in:<file>` | 在页面里求值（`in:` 适合放探针文件） |
| `tap:x,y` | 真实鼠标按下+抬起 |
| `wait:ms` / `shot:<file>` | 等待 / 截图 |
| `log` | 打印 `window.__probeLog` |

要点：

- 退出码非 0 表示页面抛了未捕获异常；结束时看 SUMMARY 的 `exceptions` / `page errors`；
- `in:` 的返回值不会被打印，探针应把结果 `window.__probeLog.push(...)` 后再 `--step log`；
- 同一会话里"找节点 → 点它 → 截图 → 再读状态"才有意义，所以步骤是**按顺序**执行的；
- 用临时 profile（默认 `work/shots/edge-profile`，可 `--fresh` 重置）避免污染真实存档。

手信显示与花盆收获回归探针（使用独立测试存档，会种植并收获两盆植物）：

```bash
node work/tools/cdp_drive.js --url http://127.0.0.1:8231/index.html --profile work/shots/bugs-regression-profile --wait 10000 --settle 2000 --step in:work/probe/souvenir_flowerpot_regression.js
```

期望返回 `passed: true`，覆盖无邀约、等待接受、有效邀约、缺失伙伴的旧状态和邀约结束后的手信显示，以及花卉/果蔬收获后的存档重载。

背包与护身符回归使用另一个独立测试存档（会替换其库存）：

```bash
node work/tools/cdp_drive.js --url http://127.0.0.1:8231/index.html --profile work/shots/packing-regression-profile --wait 10000 --settle 2000 --step in:work/probe/packing_regression.js
```

期望返回 `passed: true`：通过真实选物品界面按乱序填满背包，检查库存转移、错类型拒绝、旅行后道具槽位和一次性护身符消耗，再验证锦鲤玉佩连续两次出行可复用。

路程表、嘟嘟商店和肥料箱探针（会替换独立测试存档的领取进度和库存）：

```bash
node work/tools/cdp_drive.js --url http://127.0.0.1:8231/index.html --profile work/shots/merchant-regression-profile --wait 10000 --settle 2000 --step in:work/probe/merchant_tasks_compost_regression.js
```

期望 `passed: true`：领取重载后不再弹同一奖励，售罄窗口关闭且嘟嘟离开，补货后商人回来，肥料箱可见并能打开六格窗口。背包探针同时检查归家解锁和无食物拒绝出行。

## 第 5 层（可选）：静态检查与数值抽样

```bash
node work/tools/travel_stats.js            # 旅行收益抽样（特产/典藏/笔记/三叶草 每趟期望值）
python work/tools/audit_coverage.py        # 协议覆盖率
python work/tools/handler_census.py        # 处理函数清点
python work/tools/check_cdn_overlay.py     # 归档 CDN 与工作区资源的差异
```

## 回归纪律

1. 改引擎 → 跑第 1 层 → 重建内联引擎 → 跑第 2 层；
2. 出包 → 跑第 3 层（含 `apk_identity.py`）；
3. 涉及界面/交互的改动 → 跑第 4 层并留截图；
4. 任何"改完必须同时更新"的位置：玩家说明书（`dist/说明书.txt`）、
   `docs/设计取舍与自定数值.md`、以及本仓库的文件清单。
