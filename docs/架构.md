# 架构

## 总览

```
┌──────────────────────────────────────────────────────────────────────┐
│  路线 B（发行方式）：纯前端，无任何服务端                              │
│                                                                      │
│  work/run/web/                                                       │
│    index.html  →  js/main.min.js（客户端游戏，已打离线补丁）           │
│    __probe.js  ←  覆盖 core.Socket.prototype，把命令交给引擎           │
│    __offline-engine.js  ← 引擎 + 协议 + 数据表（构建时内联生成）        │
└──────────────────────────────────────────────────────────────────────┘
                              ▲ 同一份引擎源码
┌──────────────────────────────────────────────────────────────────────┐
│  路线 A（调试）：本地 WebSocket 服务端                                 │
│  work/run/server/{main.js, ws.js}   托管 web/ 并加载引擎               │
└──────────────────────────────────────────────────────────────────────┘
                              ▲
┌──────────────────────────────────────────────────────────────────────┐
│  work/run/engine/index.js                                             │
│    createEngine({ savePath, verbose })                               │
│      → { dispatch(cmd, data), tick(), state, ... }                    │
│    ├─ protocol.js                 244 条协议：线名 ↔ 下划线名 + 参数    │
│    └─ data/                                                          │
│         gamedata.json             60 张客户端表                        │
│         define.json               原版调参表（Tabikaeru.Define）        │
│         picture-layers.json       明信片合成图层（按 pic_id 预计算）     │
│         travel.json               目的地地图（服务端独占的表）           │
│         tables/*.json             逐表导出，便于查表                    │
└──────────────────────────────────────────────────────────────────────┘
```

## 引擎接口

引擎是一个普通的 Node 模块，不依赖浏览器也不需要网络：

```js
const { createEngine } = require('./work/run/engine/index.js');
const engine = createEngine({ savePath: 'save.json' });

// 处理一条客户端命令：返回 { reply, pushes, handled }
const { reply, pushes } = engine.dispatch('travel_load_note', {});

// 推进时间驱动的状态（出门、回家、访客、活动窗口…）
const pushes2 = engine.tick();

// 存档与状态都在 engine.state 上（可读可写，单测就是这么构造场景的）
```

- `dispatch` 的键名 = 客户端的**下划线**命令名（`travel_load_gift`），
  线上传输的键名是点号形式（`travel.load_gift`），由 `protocol.js` 双向映射。
- `pushes` 是服务端主动下发的消息（`client_load_role`、`item_update`、`notify_new_event`…），
  路线 A 会广播给 socket，路线 B 由 `__probe.js` 回灌给客户端自己的回调表。

## 路线 B 的接缝

客户端所有请求都经过 `core.SocketManage.prototype.send`，所有回包都经过它的解析函数。
`work/run/web/__probe.js` 覆写这两处：

1. `send(cmd, params, ...)` → 转成下划线名交给 `engine.dispatch`；
2. 把 `reply` 当成该命令的回包投递给客户端注册的回调；
3. 把 `pushes` 逐条投递；
4. `engine.tick()` 由页面上的定时器驱动。

因此**客户端一行都不用改**，离线化只发生在这一层。

### 浏览器里的存档

客户端原本把存档读写交给原生侧（Android 壳）。浏览器没有文件系统，
构建时将引擎的 `fs` 调用替换为一个桩：`save.json` 等文件映射到
`localStorage` 的 `frog.offline.save::<文件名>` 键，并保留
`.bak` / `.tmp` / 损坏隔离等安全副本的语义。

### 客户端侧的两处离线补丁

`work/tools/patch_game.py`（幂等，永远从原版 `js/main.min.js.clean` 出发）：

1. **进入游戏的开关**：`GameConfig.activate` 只在原生 SDK 生命周期回调里被置位，浏览器里不会发生；
2. **季节资源键钳制**：只发布了 `season11..season44` 资源包，"00" 默认键会请求不存在的文件。

## 数据文件

| 文件 | 来源 | 说明 |
|---|---|---|
| `data/gamedata.json` | 客户端加密包 `config.eab`（60 张表） | 引擎的主数据源；由 `tools/extract_gamedata.py` 等工具汇总 |
| `data/define.json` | 客户端 `Tabikaeru.Define` | 原版调参表：旅行时间、相册上限、抽奖球权重… |
| `data/picture-layers.json` | **重建物** | 明信片由客户端"只渲染、不合成"，图层顺序与坐标由数据表 + 美术资源重建 |
| `data/travel.json` | 归档的服务端表 `TravelData/*` + `MainData/Item.json` 的 `effects` | 目的地地图与物品效果；由 `tools/build_travel_data.py` 生成 |
| `data/tables/*.json` | 同上 | 逐表导出，方便直接查阅或写脚本 |

## 状态与存档

- `state` 是一个纯 JSON 对象（槽位、背包、桌子、相册、图鉴、访客、任务、活动窗口…），
  序列化即存档，因此**存档结构就是引擎的公开契约**：改动必须保持旧档可读。
- 时间统一用**秒**（Unix 时间戳）；活动窗口按 `end_time > now` 判断。
- 随机性集中在少数几处（旅行奖励、抽奖、访客、掉落），便于用统计方式做单测。

## 测试与工具的分层

见 `docs/测试与验收.md`：单元测试（引擎直调） → 打包物验收（`verify_bundle_*`）
→ 发行物验收（`verify_shipped_*`） → 真页面探针（headless Edge）。
分层的原因是引擎、内联引擎、发行包三者可能不一致，必须分别验证。
