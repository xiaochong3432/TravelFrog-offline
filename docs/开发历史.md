# 开发历史

按时间顺序记录主要改动：**做之前是什么问题 → 怎么处理 → 怎么验证**。
更细的逐条记录见 `work/run/` 下的说明与验收文件（仓库内含），
以及各专题规格 `work/spec/*.md`。

## 一、可行性确认与整体方案

- **问题**：国服客户端已停运，登录与全部玩法逻辑都在服务端，客户端只剩界面与美术。
- **处理**：确认客户端为 Egret H5，游戏代码与资源完整地打包在 `assets/game/` 内，
  只有网络层指向已停运的服务器。方案定为两条路径：
  **A** 本地 WebSocket 服务端（打通核心循环、便于抓协议），
  **B** 把同一套规则引擎内联进页面、接管 `core.SocketManage`（发行方式）。
- **验证**：客户端 `main.min.js` 中的协议列表与回调表被完整提取（244 条），
  A 路线可进入主界面并跑通出门/回家/三叶草/相册。

## 二、引擎与协议层

- 引擎实现为普通 Node 模块（`createEngine({savePath}) → {dispatch, tick}`），
  键名使用客户端的下划线命令名，`protocol.js` 负责线名映射与参数规格。
- 逐步补全子系统：商店与道具、旅行与纪念品与相册、家具与庭院与花盆、
  访客与邮件与任务、图鉴与百科、日历、抽奖、料理、故事、便利贴、扭蛋、图纸、活动。
- **重要发现**：客户端侧的 `addClover` / `addTicket` / `addHouseItem` 都是空函数，
  `consumeXxx` 只判断不扣。因此所有奖励必须由服务端真实发放并主动推送
  （`clover_update` / `item_update_ticket` / `item_update`），否则界面数值永远不变。
- **验证**：`node work/tools/engine_test.js`（现有 362 条用例）。

## 三、数据层

  同时抽出客户端内的原版调参表 `Tabikaeru.Define`。
  工具：`tools/eab_dec.py`、`tools/extract_gamedata.py`、`tools/build_define_json.py`。
- 重建明信片图层（客户端只渲染不合成）：`tools/build_picture_layers.py`。
- 关服前归档增量资源 CDN：`tools/archive_cdn_live.py`（按 `patch.json` 逐文件校验 md5）。
- **验证**：`tools/audit_coverage.py`、`tools/check_cdn_overlay.py`、发行物验收脚本。

## 四、打包与安装

| 问题 | 处理 | 验证 |

## 六、存档安全

- **问题**：PC 端偶发"存档被重置"。
- **处理**：定位为端口/地址变化导致浏览器换了存储分区（见上表），
  并在引擎侧加固：写入后回读校验、`save.json.bak` / `.tmp` 保留、
  损坏存档隔离为 `.corrupt-<时间戳>` 而不覆盖、导入存档为显式覆盖语义、
  悬浮球内提供存档导出/导入与存档状态面板。
- **硬约束**：旧存档必须始终可读 —— 新增字段一律可选、缺失时惰性生成。
- **验证**：`engine_test.js` 的存档安全用例、`tools/check_save_robustness.js`、
  `verify_bundle_save.js`。

## 七、试玩反馈修正（第一批）

| 反馈 | 根因 | 处理 |
|---|---|---|
| 小问答选完后确认按钮变灰 | 客户端传来的选项下标是 **1 起算**，而生成的正确答案从 0 起算，随机到 0 时该题永远答不对 | 正确答案固定为 1–3 的真实选项，并改为"该邻居真正偏爱的食物" |
| 手工品「祈愿物」日期异常 /「印章」图片空白 | 卡片日期读的是行数据里的 `stamp_time`，而此前只写了内部时间；印章状态被推到表里不存在的档位 | 写入 `stamp_time`，印章状态限制在表定义范围内 |
| 回家后背包物品与桌上不一致 | 回家归还物品时只按 id 顺序回填，未按槽位类型（便当/护身符/道具）回位 | 记录来源槽位与来源区域（背包/桌子）并原位归还 |
| 旅行时帽子留在家里 | 客户端在特定事件后重绘角色 | 补一次角色状态刷新推送 |
| 「伴蛙前行」的奖励无法领取 | 累积计划奖励 `task_get_list_reward` 未实现 | 按客户端 `taskData` 的 `list_type` 实现分档领取与已领状态 |
| 周末的小插曲选项数量不对 | 分支条件写错 | 按客户端数据修正 |
| PC 端打开门槛 | 需要 Python 或改执行策略 | 提供 .NET 启动器 |
| 相册里小青蛙位置异常 | 立绘锚点取错 | 按数据表的锚点与画布尺寸重算图层坐标 |

## 九、目的地系统

- **问题**：攻略资料里的"纪念品/特产按目的地""博物馆门票""特殊路线""彩叶幸运草补缺图"等机制此前未实现，
  表现为照片与特产在全表中均匀随机、护身符不产生效果。
- **处理**：定位到这些机制依赖**服务端独占的地图数据**（客户端检索 `TravelData` 零命中），
  而这些数据已随 CDN 归档取得。整理为 `data/travel.json` 并实现表驱动的目的地系统：
  区域选择、沿邻接行走、按路段标签给照片、按节点给特产与纪念品、终点照、
  特殊路线（需道具）、博物馆门票直达、旅行笔记、彩叶幸运草补缺图。
- **关键判定**：邻接必须取双向并集（否则五座博物馆不可达）；`wayType` 与工具族的对应关系由三处数据互相印证。
- **验证**：`engine_test.js` 新增目的地相关用例；`tools/travel_stats.js` 抽样收益；
  实页面探针 `tools/probe_travel_map.js`。

## 十、V3 接手（2026-09-15）

接手团队（`nixiaoyao999-code`）发布了 V3 离线包（包名 `com.travelfrog.offline`，其 Gradle 工程见
`android-apk/`）。在**保留其包内其余内容**的前提下，本仓库做了三处改动，并用本仓库的打包链与
密钥重新出包（`com.frog.offline`，versionCode 3）：

| 改动 | 落点 |
|---|---|
| **存档导出修复** | 导出优先走原生桥 `FrogNative.exportSave(name, json)`：Android 10+ 直接写 `内部存储/Download` 并回报路径；旧系统弹「保存到」窗口，保存完成后经 `window.__saveExported()` 回填位置；失败/取消会明说。桥在 `work/app/src/.../MainActivity.java`，页面侧在 `work/run/web/__probe.js` |
| **声明人** | 开始页《权利归属与告知声明》的声明人改为「旅行青蛙离线版制作组」（`work/run/web/index.html`） |
| **帮助菜单** | 「联系客服」→「制作人员」并列出四位制作者。该按钮是 `eui.Image`、**文字画在贴图里**，因此重绘了 `resource/China/eab/system.eab` 的 `button_02_png`，并**同步更新 `version.json` 里登记的 md5** |

校验（`work/tools/verify_handover_apk.py`）：三处改动齐备、`system.eab` 的 md5 与 `version.json` 一致、
除承包商引擎外全部资源逐字节相同、整机验收 32/32。

两条必须说清的结论：**该包不是 V3 的升级包**（包名与签名都不同，只能并存）；
**V3 的存档带不过来**（它存在自己 App 的 `file://` origin 下，且其原生层没有导出桥）。

与仓库内容的对应关系（本次整理后）：

- 运行时代码与页面代码在 `work/run/web/`，**已包含上述三处改动**；
- 客户端资源（`resource/**`，约 260 MB）按仓库规矩**不入库**，由 `work/tools/extract_game.py` 本地生成；
- 承包商的引擎包（`__offline-engine.js`，sha1 前缀 `e41d91b8`）与其 `__probe.js` 变体只存在于本地的
  V3 载荷（`work/run/v3web/`）与 `dist/TravelFrog-offline-V3.apk`，**不进仓库**（客户端代码/生成物）；
  两者的差异已用 `work/tools/js_code_diff.py` 核对：**实际代码只差两处同义写法**，本仓库的版本更新一版；
- V3 相关工具：`work/tools/{extract_v3_payload,verify_handover_apk,v3_credits_and_export,install_help_button,help_view,skin_usage,fix_export_location}.py`。

## 十一、手信、花盆与行李修复（2026-09-16）

- 无伙伴邀约时隐藏手信页：`DrawingModel.initModel` 默认等待，`BagTable.onComplete` 同时检查伙伴和已接受/锁定状态；补丁由 `work/tools/patch_game.py` 重放。邀约完成后回到等待状态，读取旧存档时修复“已接受但伙伴为 -1”的残留状态，并拒绝接受不存在的邀约。
- 花盆按实际植物发放收获物：依据 `flowerpotData.plant` 与 Item 表匹配，花卉使用 type 14/sub_type 6 的完整品种名称，果蔬使用 type 3 的物种名称。35 个植物变种都有对应产物，不再从农产品池随机挑选；未知植物保留原槽位，花卉不写入特产图鉴。
- 背包和桌子按客户端 `BagItem` / `DeskItem` 的槽位类型校验，`ItemModel.setBagData` / `setDeskData` 同时检查类型和库存，界面不绘制被拒绝的物品。引擎补齐装入扣库存、取出返库存、替换归还原物品的操作；旧存档错位物品按类型归位。
- 护身符在出门后消耗，唯一复用例外是 Item 1001（玉佩，客户端描述为“看上去很像锦鲤的玉佩”）；旧旅行计划也不再归还已消耗的护身符。旅行效果仍按已携带物品计算。
- 回归用例覆盖全部植物变种、所有背包/桌子槽位、全部护身符与旧存档修复；真实页面探针见 `work/probe/souvenir_flowerpot_regression.js` 和 `work/probe/packing_regression.js`。
