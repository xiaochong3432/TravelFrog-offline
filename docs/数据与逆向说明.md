# 数据与逆向说明

本项目不发明数据：能用客户端表或客户端代码证明的，一律以客户端为准。
本文说明这些数据是怎么拿到、怎么重建、哪些是重建物。

## 1. 客户端数据表（60 张）

客户端的配置打包在 `assets/game/resource/China/config.eab`。它是 **XXTEA 加密变体**，
但客户端自己写了怎么解：

- 解密入口：`eab.decode`
- 密钥：`Utils.simpleEncrypt("r]|lnf\x80X\x81U\x82aq_r", 13)`
- 两个实现坑：打包是**小端**；密钥需要补零到 16 字节
- manifest 里每项的 `f` 是**路径**而非偏移，计算载荷位置要**累加各项的 `s`**

工具：`work/tools/eab_dec.py`、`work/tools/eab_decode.js`、`work/tools/extract_gamedata.py`。
产物：`work/run/engine/data/gamedata.json`（60 张表）与 `work/run/engine/data/tables/*.json`。

主要表：`Item`、`shopData`、`Shop`、`GiftData`、`Prize`、`lotteryData`、`Collection`、`Specialty`、
`Picture`、`PictureTag`、`GoalNumber`、`Achieve`、`taskData`、`calendarData`、`cookingData`、
`furnitureData`、`furnitureShopData`、`flowerpotData`、`compostData`、`decoration`、`museumData`、
`museumDay*`、`Note`、`story`、`visitors`、`TravelFriends`、`drawing*`、`PartyCakeData`、
`springCard`、`greetCard`、`capsuleData`、`tumblerData`、`stampData`、`pray*`、`encyclopedia`、
`resources`、`zh-CN` 等。

### 原版调参表

`assets/game/js/main.min.js` 内的 `Tabikaeru.Define` 被抽成 `data/define.json`：
旅行最短时间、相册与背包上限、抽奖球权重、访客节奏、四叶草参数等。
引擎优先使用这里的原始数值，仅在为可玩性缩短节奏时以显式常量覆盖（见自定数值文档）。

## 2. 明信片图层（重建物）

客户端的相册代码**只渲染、不合成**：它读服务端下发的 `layers` 数组
（`[资源id, x, y]`，即 500×350 画布上的左上角），逐层贴图后一次性画到画布上。
原始服务器已不存在，因此 `data/picture-layers.json` 是**重建物**：

- 依据：`Picture` 表的 `backImage` / `frontImage` / `frogPose` / `frogPos` /
  `travelerPos` / `travelerPose` 列 + 随包美术；
- 生成器：`work/tools/build_picture_layers.py`；
- 校验：渲染对照（`work/tools/render_pictures.py`）与发行包验收
  （`verify_shipped_layers.py`）。

已知不足：**天/海/花/远山这类"中间横带"的官方摆位规律没有从数据中推出**，
这些图层仍按数据表自身坐标绘制（贴在画面上沿）。贴地类横带（地面/屋顶/海堤）已正确。

## 3. 目的地地图（服务端独占的表）

旅行地图**不在客户端**：`main.min.js` 里检索 `TravelData` 零命中，
它原本只存在于服务端。这份数据已从 CDN 归档中取得：

```
resource/China/config/TravelData/{Area,Node,NodeConnect,NodeEdge,NodeGoal,NodeItem}.json
resource/China/config/MainData/Item.json      ← 含 effects 列（客户端自己的 Item 表没有这一列）
```

`work/tools/build_travel_data.py` 把它们整理为 `data/travel.json`（约 92 KB），
语义与算法见 `docs/目的地系统.md`。

## 4. CDN 归档

关服前，客户端的增量资源仍可通过热更 CDN 取得。`work/tools/archive_cdn_live.py`
按 CDN 自己的 `patch.json`（946 项，带 md5 与大小）逐文件下载并**逐字节校验 md5**，
不一致时报告而不静默保留。归档位于 `work/cdn/`（默认不入库，见 `.gitignore` 说明）。

## 5. 客户端资源与"最小仓库"

`work/run/web/resource/`（约 260 MB：图集、音频、视频、EAB 资源包）属于原权利人，
默认不放进仓库。重建方式：

```bash
python work/tools/extract_game.py      # 从 base.apk 提取 assets/game/
python work/tools/patch_game.py        # 幂等离线补丁（从 main.min.js.clean 出发）
python work/tools/bundle_engine.py     # 重建内联引擎
```

需要自带资源的完整副本：`python work/tools/stage_repo.py --with-assets`。

## 6. 方法论：证据可复现

- 每条逆向结论都记下**函数名 + `main.min.js@字符偏移`**（`work/spec/*.md`），
  可直接用 `work/tools/jsctx.py` / `dump_chars.py` / `defoffset.py` 复核；
- 客户端片段 dump 存放在 `work/spec/_dumps/`，解出的权威数据表在 `work/spec/data/`；
- 被文档引用的过程 dump（`work/*.txt`）随仓库一起提供，便于对照；
- **不要用本项目自己的实现去验证自己的实现** —— 发行物验收
  （`verify_shipped_*.py`、`apk_identity.py`）检查的始终是打进包里的那份文件。
